1 · What it is

Pineapple Lover is a private web dashboard for planning an Indonesian wedding. Two people — the bride and groom — sign in with their Google accounts and edit the same live planning data from their own phones or laptops. Every edit one person makes shows up on the other person's screen within a second.

It tracks the things an Indonesian wedding actually needs: the budget, the seserahan (gift trays), the mahar / mas kawin (dowry), the ceremony costs, guests, vendors, adat (customary) rituals, legal paperwork (KUA/Simkah), and the day-of rundown.

One sentence: it's a shared spreadsheet-style planner with a wedding-specific structure, live sync between two people, and a Google login so nobody else can see or touch the data.

There are two generations of this app:

VersionWhatWhere
Vanilla (legacy)The original — one single index.html file with all HTML, CSS and JS inlined.~/claudia/wedding-legacy (archived, no longer live)
React (current)A proper component-based rewrite with Redux state management and a build step. This is what's live.~/claudia/pineapple-lover → deployed to GitHub Pages

This report describes the React version, which is the one now serving at the live URL.

2 · Functional walkthrough — the 11 tabs

The app is a single page with a centered row of tabs. You click a tab, that section shows. Here's what each does:

1. Overview

The landing screen. Shows the couple's names, the wedding date, a live countdown ("X days to go"), and summary cards pulling totals from the rest of the app (total budget, how much is allocated, guest count, etc.). Read-at-a-glance.

2. Budget

Read-only roll-up. You don't type numbers here — it derives them. It adds up what the Ceremony, Seserahan and Mahar tabs cost and shows you: total budget vs. allocated vs. remaining, plus a breakdown table by category. Change a price anywhere else and this updates itself.

3. Wedding Ceremony

An itemized cost table — venue (gedung), catering, MUA (makeup), decor, WO (wedding organizer), etc. Columns: Item, Qty, Unit price, Vendor, Paid?, Notes, and a Marketplace link. Totals at the bottom. Add/delete rows freely.

4. Seserahan

The gift-tray checklist — same itemized table shape as Ceremony, but "Paid?" reads "Bought?". This is where the bride's imported gift list lives (shoes, bags, cosmetics, prayer items…), each with a price, vendor and a Shopee/Tokopedia link.

5. Mahar & Mas Kawin

The dowry items — again the same itemized table. Tracks things like the mahar money, gold, prayer set, etc.

6. Guests

Guest list table: Name, Side (Groom/Bride), Category (Family/Friends/Work/VIP), Invited #, RSVP status, Table assignment.

7. Vendors

Vendor tracker: Category, Vendor, Contact, Quote, DP (down payment) paid, Booked?, Notes. Keeps the money and the contacts in one place.

8. Adat & Rituals

A checklist of customary/traditional ceremony steps (siraman, midodareni, akad, resepsi, etc.) — tick them off as you plan each one.

9. Legal

A checklist for the paperwork trail — KUA registration, Simkah, documents (KTP, KK, N1–N4 forms), pre-marital requirements. Tick-box style.

10. Rundown

The minute-by-minute day-of schedule: Time, Event (acara), PIC (person in charge). Add a row per slot.

11. Backup

Data controls: Export everything to a wedding-data.json file (hard backup), Import a JSON file to replace current data, Sign out, and Reset all (wipe and start fresh, with a confirm prompt).

Three of the tabs (Adat, Legal, parts of Overview) are checklists; six (Ceremony, Seserahan, Mahar, Guests, Vendors, Rundown) are editable tables; Budget is a derived read-only roll-up. That's the whole functional surface.

3 · How two people use it together

  1. Both partners open the same URL and sign in with Google.
  2. Only two specific Google accounts are allowed in (see Authentication); everyone else is blocked.
  3. They share one workspace keyed by a WEDDING_ID ("pineapple-wedding") — same id = same data.
  4. When one edits a cell, the change is pushed to Firebase; the other's browser is listening and re-renders instantly.
  5. Everything is also cached in each browser's localStorage, so the app still opens and shows the last known data even with no connection — it just re-syncs when it reconnects.
Known trade-off: sync is whole-document and "last write wins." If both people edit the same cell at the same second, the last save wins and the other's keystroke can get overwritten. For a two-person planner this is fine in practice — you're rarely in the exact same cell at the exact same moment.

5 · How data flows (the big picture)

This is the mental model for the whole app. Read it once and everything else clicks:

USER TYPES IN A CELL │ ▼ dispatch(setCell(...)) ← a Redux "action" describing the change │ ▼ weddingSlice reducer ← updates the single source of truth (the store) │ ├──────────────► React re-renders any component that reads that data │ (Budget roll-up, Overview cards, the table — all at once) │ ▼ syncMiddleware (runs after every wedding/* action) │ ├──► persistLocal(state) → saves to localStorage (offline cache) │ └──► scheduleCloudPush(state) → debounced 400ms → writes to Firebase │ ▼ FIREBASE REALTIME DB │ ▼ (onValue listener) THE OTHER PERSON'S BROWSER │ ▼ dispatch(replaceAll(remoteData)) │ ▼ their store updates → their UI re-renders

The key idea: components never talk to each other or to Firebase directly. They only read from the store and dispatch actions. Everything else (saving, syncing, deriving totals) hangs off that one pipe.

6 · The Redux store

There's one store with two "slices" (sub-sections of state):

wedding slice — all the planner data

{
  p1, p2,            // partner names
  wdate,             // wedding date
  totalBudget,       // the budget ceiling
  mahar, timeline,   // misc fields
  ceremony:   [ [item, qty, unitPrice, vendor, paid, notes, link], ... ],
  seserahan:  [ ...same row shape... ],
  maharkawin: [ ...same row shape... ],
  guests:     [ [name, side, category, invited, rsvp, table], ... ],
  vendors:    [ [category, vendor, contact, quote, dp, booked, notes], ... ],
  rundown:    [ [time, event, pic], ... ],
  adat:       [ {text, done}, ... ],   // checklists
  legal:      [ {text, done}, ... ],
}

Its reducers (the only ways to change data) are deliberately generic, so one set covers every table:

ReducerWhat it does
setFieldSet a top-level field (names, date, budget).
setCellSet one cell in one row of one table.
addRow / delRowAdd / remove a row in any table.
toggleCheck / addCheck / delCheckChecklist operations (Adat, Legal).
replaceAllSwap the whole dataset — used by cloud sync and JSON import.
resetAllWipe back to the seed defaults.

auth slice — who's signed in

Holds { user, status, error }. status is connecting / local / signed-in. The UI uses this to decide whether to show the Google sign-in gate or the dashboard.

Derived numbers aren't stored — they're computed on the fly by selectors (selectors.js): budgetRollup(), sectionStats(), sumCol(). That's why the Budget tab is always correct without anyone "recalculating" it.

7 · The cloud-sync layer

Two files do all the Firebase ↔ Redux bridging:

src/cloud.js

  • initCloud(store) — starts the auth listener (onAuthStateChanged). When a user signs in, it begins subscribing to their wedding's data.
  • subscribe() — attaches Firebase's onValue listener. When remote data changes, it dispatches replaceAll to update the local store.
  • scheduleCloudPush(state) — debounced (400ms) write up to Firebase, so rapid typing doesn't hammer the network.
  • signIn() / logOut() — Google popup sign-in and sign-out.

src/syncMiddleware.js

Redux middleware that runs after every wedding/* action: it saves to localStorage and (unless the change came from the cloud) schedules a push back up.

The echo-guard. Without care you'd get an infinite loop: remote change → update store → middleware pushes it back up → triggers another remote change → … The fix is an applyingRemote flag: while applying a change that came from Firebase, the middleware skips the push. Plus a JSON.stringify compare so identical data never re-writes.

8 · Authentication & lockout

Sign-in is Google only (Firebase Auth with GoogleAuthProvider + signInWithPopup). There are no passwords.

Letting someone sign in is not the same as letting them read the data. The real gate is the Firebase Realtime Database security rules, which restrict read/write to two specific user IDs:

{
  "rules": {
    ".read":  "auth != null && (auth.uid === 'UID_ONE' || auth.uid === 'UID_TWO')",
    ".write": "auth != null && (auth.uid === 'UID_ONE' || auth.uid === 'UID_TWO')"
  }
}

Anyone else can click "sign in with Google," but Firebase refuses to hand them any data. That's the lockout.

The Firebase web config is not a secret. The apiKey/projectId in src/config.js are safe to publish — they only identify the project. Security comes entirely from the DB rules above and the list of Authorized Domains in Firebase Auth.

Two reusable components carry most of the UI:

  • DataTable.jsx — a generic editable table. You hand it a tableKey (which slice field) and a cols definition; it renders inputs, handles edits, add/delete rows, and opens marketplace links. Powers 6 tabs.
  • Checklist.jsx — a generic tick-list. Powers Adat & Legal.

Because the tables are config-driven (columns defined as data in config.js), adding a column or a whole table is editing a list, not writing new UI.

10 · Data model (row shapes)

Tables are arrays of arrays (each row is an array of cell values). The column order is the schema — it's defined once in config.js under COLS:

TableColumns (in order)
ceremony / seserahan / maharkawinItem · Qty · Unit price · Vendor · Paid(or Bought) · Notes · Marketplace link
guestsName · Side · Category · Invited # · RSVP · Table
vendorsCategory · Vendor · Contact · Quote · DP paid · Booked · Notes
rundownTime · Event (acara) · PIC
adat / legalObjects: { text, done }

Each column has a type (text / num / select / link) that tells DataTable how to render that cell's input.

11 · Security & cost notes

  • Cost: $0. GitHub Pages (free), Firebase Spark plan (free tier) — a two-person planner is nowhere near the limits.
  • Firebase web config is public-safe — do not treat the apiKey as a secret. The DB rules are the real control.
  • Data access is locked to two UIDs via DB rules. Add a third person only by adding their UID there.
  • Authorized Domains in Firebase Auth must include the live host (sennafaris28.github.io) or Google sign-in is rejected. The URL didn't change in this migration, so this still holds.
  • Backups: the Backup tab's JSON export is your disaster recovery. Export occasionally.

12 · Hosting & deployment

The app is hosted free on GitHub Pages at https://sennafaris28.github.io/pineapple-lover/. Since Vite needs a build step, "deploying" means building the static dist/ and getting it onto Pages. There are two paths, and this project is set up for both:

Path A — GitHub Actions (the intended, automatic way)

A workflow at .github/workflows/deploy.yml runs on every push to main: it checks out the repo, installs deps, runs npm run build, and publishes dist/ to Pages. Push code → site updates itself. This needs Pages set to "GitHub Actions" source.

Current status: Actions is temporarily blocked because the GitHub account has a billing lock ("the job was not started because your account is locked due to a billing issue"). Until that's resolved, the automatic path can't run. Clear the billing issue in GitHub → Settings → Billing, then switch Pages back to "GitHub Actions" and it'll work.

Path B — Manual build → gh-pages branch (the current fallback)

While Actions is locked, the site is served from a gh-pages branch that holds only the built files. To re-deploy after a change:

# from ~/claudia/pineapple-lover
npm run build

# copy dist into a throwaway folder, publish it as gh-pages
rm -rf /tmp/gp && cp -r dist /tmp/gp && touch /tmp/gp/.nojekyll
cd /tmp/gp
git init -b gh-pages
git add -A && git commit -m "Deploy build"
git push https://github.com/sennafaris28/pineapple-lover.git gh-pages --force

Pages is currently pointed at: build_type: legacy, source branch gh-pages, path /.

Bottom line: the site is live via Path B right now. The moment billing is sorted, flip Pages source back to "GitHub Actions" and future deploys become a plain git push.

13 · Step-by-step: build it from scratch

This is the condensed recreate guide. (The repo's TUTORIAL.md is the long version with every concept explained.) Assumes Node.js 18+ installed.

Step 1 — Scaffold the project

npm create vite@latest pineapple-lover -- --template react
cd pineapple-lover
npm install
npm install @reduxjs/toolkit react-redux firebase

Then in vite.config.js set base: './' so assets resolve under the Pages sub-path.

Step 2 — Create a Firebase project (free)

  1. Go to console.firebase.google.com → Add project.
  2. Build → Realtime Database → Create (pick a region, e.g. Singapore asia-southeast1).
  3. Build → Authentication → Sign-in method → enable Google.
  4. Project settings → Your apps → Web app → copy the firebaseConfig object.

Step 3 — Config file

Create src/config.js: paste FIREBASE_CONFIG, set a WEDDING_ID, define the TABS list and the COLS column definitions (see §10). Add cloudEnabled = !!FIREBASE_CONFIG.databaseURL so the app runs local-only if you blank the URL.

Step 4 — Redux store + slices

  1. src/seed.js — a seed() function returning the default data object.
  2. src/slices/weddingSlice.js — createSlice with the reducers in §6. Load initial state from localStorage, else seed.
  3. src/slices/authSlice.js — { user, status, error }.
  4. src/store.js — configureStore combining both slices and adding the sync middleware.

Step 5 — The sync layer

  1. src/firebase.js — init the Firebase app, auth, database (only if cloudEnabled).
  2. src/cloud.js — initCloud, subscribe (onValue → replaceAll), scheduleCloudPush (debounced), signIn/logOut, plus the applyingRemote echo-guard.
  3. src/syncMiddleware.js — after each wedding/* action: persistLocal + (if not applying remote) scheduleCloudPush.

Step 6 — Components

  1. DataTable.jsx — generic editable table driven by a cols prop; dispatches setCell/addRow/delRow.
  2. Checklist.jsx — generic tick-list.
  3. Header.jsx, Nav.jsx (centered tabs), AuthGate.jsx (Google sign-in screen), Cards.jsx (summary cards).
  4. components/tabs/* — one small component per tab, mostly wrapping DataTable or Checklist with the right tableKey.
  5. selectors.js — budgetRollup, sectionStats, sumCol for the derived numbers.

Step 7 — Wire it up

src/main.jsx: call initCloud(store), then render <Provider store={store}><App/></Provider>. App.jsx shows the AuthGate when cloud is on and nobody's signed in, otherwise Header + Nav + the active tab.

Step 8 — Run it

npm run dev      # http://localhost:5173
npm run build    # outputs dist/
npm run preview  # preview the built bundle

Step 9 — Lock the database

Sign in with both real Google accounts once (so Firebase creates their UIDs). Grab each UID from Firebase Auth → Users. Then set Realtime Database → Rules to the two-UID rule shown in §8. Publish.

Step 10 — Deploy to GitHub Pages

  1. Push the repo to GitHub.
  2. Add .github/workflows/deploy.yml (build Vite → upload dist/ → deploy-pages).
  3. Repo Settings → Pages → Source: GitHub Actions.
  4. In Firebase Auth → Settings → Authorized domains, add your username.github.io domain.
  5. Push → the workflow builds and publishes. (If Actions is unavailable, use the manual gh-pages fallback in §12, Path B.)

14 · How to add a new tab (worked example)

Say you want a "Honeymoon" cost table. The config-driven design means this is four small edits, no new UI logic:

  1. config.js — add ['honeymoon', 'Honeymoon'] to TABS, and a honeymoon: entry under COLS with your columns.
  2. seed.js — add honeymoon: [] (or some starter rows) to the seed object.
  3. weddingSlice.js — nothing to change; the generic reducers already handle any table key.
  4. components/tabs/Honeymoon.jsx — a 6-line component rendering <DataTable tableKey="honeymoon" cols={COLS.honeymoon} />, then register it in App.jsx's tab map.

That's the payoff of the generic table + config-as-data approach: new sections are declarative.
